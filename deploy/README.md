# Deploy

Every app is deployed from **one description**: [`targets.json`](targets.json). The workflows never name a host path,
a build command or an exclude list; they call [`deploy.mjs`](deploy.mjs), which reads the target. Plan and hosting
layout: `agents/PLATFORM.md` → "Hosting layout & deployment". The checklist of every production secret and variable is
the root [`.env.example`](../.env.example).

## Layout on the host (all-inkl, one FTP account)

```
<ftp root>/
├── viewer/dist/   ← scutoons.com, www.scutoons.com     target "viewer"   (viewer/build)
├── admin/dist/    ← admin.scutoons.com                 target "admin"    (admin/build)
├── creator/dist/  ← creator.scutoons.com               target "creator"  (creator/build)
├── shop/dist/     ← shop.scutoons.com                  target "shop"     (shop/build)
├── qr/            ← qr.scutoons.com  (docroot qr/public/)   target "qr"  (qr/, plain PHP)
├── api/           ← api.scutoons.com (docroot api/public/)  target "api" (server/ + vendor/ + config.php)
│   ├── storage/   private (batches, keys) – never uploaded, never deleted
│   └── config.php generated by the deploy from the production environment
```

## targets.json

| Key | Meaning |
|---|---|
| `order` | deploy order (api → qr → frontends); only these are deployed automatically |
| `targets.<app>.status` | URL answering with the live `git_sha` (version.json / API health) – `deploy/changed.mjs`, `npm run deploy:status` |
| `watch` | paths whose change needs a redeploy of the target (`dir/**` or a file; `!pattern` excludes, e.g. the content seed) |
| `protocols.<p>.credentials` | environment variable names of the host credentials (`ftp`: `FTP_SERVER`, `FTP_USERNAME`, `FTP_PASSWORD`) |
| `targets.<app>.source` | the app folder in the repo |
| `setup` | what CI installs first: `npm` (npm ci), `php` (PHP 8.3 + Composer) |
| `protocol`, `remote` | where it goes: protocol + path below the host root (`viewer/dist/`, `api/`, …) |
| `build` | build command (npm apps: at the repo root, result in `output`; `stageFirst` apps: inside the staging copy, e.g. `composer install --no-dev`) |
| `buildEnv` | variables handed to the build (`NAME` or `NAME=${OTHER}` to rename) – unset ones are left out, the app's default applies |
| `include` / `exclude` | globs (`**`, `*`, `?`) relative to the output / source; only matching files are staged and uploaded |
| `protect` | remote paths the upload never touches – neither overwritten nor deleted (api: `storage/**`, `db/**`, `logs/**`) |
| `version` | where `version.json` goes in the upload |
| `generate` | files written from environment variables: `php-define` (server `config.php`) or `php-return` (qr `config.php`); `${VAR}` unset/empty → the key is left out |
| `reminder` | printed as a warning in every run (api: DB migrations) |

## deploy.mjs

```sh
node deploy/deploy.mjs <app|all> [--dry-run] [--skip-build] [--list=all|summary] [--github] [--setup]
```

1. **build** – the target's `build` (skip with `--skip-build`)
2. **stage** – copies what `include`/`exclude` select into `.deploy/<app>/` (gitignored) – exactly what gets uploaded
3. **version** – writes `version.json` (`app, version, git_sha, built_at, shared`) at `version`
4. **generate** – writes `config.php` etc. from the environment
5. **plan** – lists every file → `<protocol>://$FTP_SERVER/<remote><path>`, the protected paths and the reminder

It never uploads. `--github` writes the plan as step outputs for `.github/workflows/deploy-app.yml`, which uploads
(FTP: `SamKirkland/FTP-Deploy-Action`, which only syncs changed files and keeps `.ftp-deploy-sync-state.json` in each
remote folder; `protect` becomes its `exclude`). `--setup` prints `npm=…`/`php=…` for the job.

Local dry run of everything (builds included), e.g. before a release:

```sh
node deploy/deploy.mjs all --dry-run --list=summary
node deploy/deploy.mjs api --dry-run            # every file of one app
```

## Workflows (`.github/workflows/`)

| Workflow | Runs on | Does |
|---|---|---|
| `deploy.yml` | push to `main`, a tag `deploy-*` (= all), manual (apps `changed` / `all` / `viewer,admin`; dry run) | **the** deploy: plan → API / qr tests if needed → the targets one at a time in `order` |
| `deploy-app.yml` | called by the others | the steps for one target: Node, `--setup`, npm ci / PHP, `deploy.mjs --github`, upload (one retry after 60 s), reminder |
| `viewer.yml`, `shop.yml`, `creator.yml`, `admin.yml`, `embassy.yml` | manual only (with dry run) | deploy that one app |
| `deploy-all.yml` | manual (optional dry run) | lists the DB migrations, then api → qr → frontends one at a time (the cutover runbook's button) |
| `qr.yml` | PR touching `qr/**`; called by `deploy.yml` | checks: `php -l`, offline smoke test |
| `server.yml` | PR touching `server/**`; called by `deploy.yml` | PHPUnit (MariaDB, docker/compose.yml) + PHPStan |

**One upload at a time.** all-inkl drops parallel FTP connections (ECONNRESET, 2026-10-02), so every deploying workflow
shares the concurrency group `production-deploy` and `deploy.yml` runs its targets with `max-parallel: 1`. A run waiting
in the group replaces an older waiting one – nothing is lost, because:

**What gets deployed is decided by what is live**, not by the push: `deploy/changed.mjs` reads each target's live
`git_sha` (`status` URL) and deploys it when files under its `watch` paths changed since that commit (or the commit is
unknown). A failed, cancelled or skipped deploy is therefore picked up by the next run – or by a manual run of
`deploy.yml` with apps `changed`.

**What is live:** `npm run deploy:status` – every target's live commit next to `origin/main` (exit code 1 if one is
behind or unreachable). `npm run deploy:changed` prints what the next run would deploy.

All deploy jobs use the GitHub environment **`production`**. Secrets and variables reach `deploy.mjs` as JSON
(`toJSON(secrets)`, `toJSON(vars)`), so a new value needs only `targets.json` + the environment, not a workflow edit.

## Versions

Every app and shared package has a semver `version` (`package.json`; PHP apps: `composer.json`) and a `CHANGELOG.md`.
Each build writes `version.json` into its output (`npm run build` → `node ../deploy/version.mjs build`; qr/api via
`deploy.mjs`): `{ app, version, git_sha, built_at, shared: { "@scutoons/api": "0.1.0", … } }`. Deployed:
`https://scutoons.com/version.json`, `https://admin.scutoons.com/version.json`, … and `https://qr.scutoons.com/version.json`;
the API reports its own in `GET /api/health/` (`version`, `git_sha`, `built_at`). `GET /api/admin/versions` (role
admin) fetches all of them (`VERSION_URLS` in the server settings) for the admin dashboard.

Bump the app's version and add a CHANGELOG entry when a change is released; bump a shared package when its public API
changes (the dashboard shows which shared versions each app was built with).

## Moving a target to bunny.net or Cloudflare later

The workflows do not change; only `targets.json`, the environment and one upload step in `deploy-app.yml`:

1. **bunny.net Storage** (static app or media): add a protocol, e.g.
   `"bunny": { "credentials": { "zone": "BUNNY_STORAGE_ZONE", "password": "BUNNY_STORAGE_PASSWORD", "region": "BUNNY_REGION" } }`,
   set the target's `"protocol": "bunny"` and `"remote"` to the path in the storage zone, add those secrets to
   `production` (+ `.env.example`), and add a step in `deploy-app.yml` with
   `if: steps.plan.outputs.protocol == 'bunny'` that uploads `steps.plan.outputs.local_dir` (e.g. `lftp` against the
   zone's FTP endpoint, or the Storage HTTP API with `curl -T`), then purges the pull zone. Point the subdomain (CNAME)
   at the pull zone.
2. **Cloudflare Pages** (static app): `"protocol": "cloudflare-pages"`, `"remote"` = the Pages project name, secrets
   `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`, a step `npx wrangler pages deploy <local_dir> --project-name <remote>`.
   Custom domain in the Pages project; remove the all-inkl subdomain afterwards.
3. PHP apps (qr, api) stay on all-inkl – they need PHP. Only their static assets could move.
4. Test with a dry run (`workflow_dispatch` → dry-run), deploy, check `https://<host>/version.json`, keep the old
   folder until the new host has served a release (rollback = point DNS back).
