# RIG-EDITING — the rig designer: where instruments are written, patched, wired and kept

## 1. In one sentence
**One rig designer in the creator, where a creator writes or patches an instrument (Rust code or nodes), hears it, maps its parameters and assigns it to a character; the code is compiled into modules the engines run; the creator's work is a draft like any catalog document and goes live through the normal review and publish – nothing is saved by readers, nothing is promoted from the audience.**

(The submit / promote part of this quote was dropped the same day: "remove the submit flow entirely".)

## 2. The rig designer – four tabs (the owner's)
1. **Parameters** – what the instrument shows: only what its Rust code makes public (`#[param]`, §4) or what its graph exposes. Per parameter: label (de / en), range, curve, default; the mappings (MIDI CC, face, motion, pad, stick – today's `Mapping`). No parameter can be invented here – the code is the source.
2. **Nodes** – the graph: built-in node kinds and compiled modules (§3) as boxes, links as cables – Max/MSP, Unreal Blueprints, TouchDesigner. **Read-only first** (shows the patch, live values on the cables, the being's hoses are the same graph); editing follows (#203: add a node, drag a link, type-checked, the matrix on a phone).
3. **Rust** – a code editor like Shadertoy's: one tab per file, add / rename / remove files, Save, **Compile**. Only a compile that succeeds hands the logic to the other tabs (new parameters appear in 1, the module's ports in 2). Debugging: §5.
4. **Assignment** – which character (persona, mood) plays it, the rig's tracks and presets per mood, routes into the being's look, the phone deck's sticks, and **scene and world variables** (KANON's story variables, the scene's state) feeding parameters. The same is reachable from code: the module API reads globals (tempo, the character's mood / persona / energy, scene and world variables, §4) – "this will grow".

Beside the tabs, always: **Play** (the engine runs what is open, on this device), the preset bar (save as a draft, derive, the lineage). Publish and review are the creator's normal ones (§6).

## 3. One model, two ways to write an instrument
- An **instrument** stays what it is (research/INSTRUMENTS.md §1): a graph of nodes + `out` + `expose` + rights.
- A node is either a **built-in kind** (graph.rs: osc, fm, lfo, walk, events …) or a **module** = compiled code (new). A module declares ports and parameters; once compiled it is a node kind like the built-ins, usable in any graph.
- So "code form" and "node patching" are not two systems: a code patch is a module (often with a one-node graph around it), a node patch wires modules and built-ins. Presets, lineage, rigs, `Rig::play`, the validator stay exactly as they are; modules add one thing to the node kinds: kinds that come from the library instead of graph.rs.

## 4. The module: what code sees, how it runs
- **A crate per module** against a small SDK crate (`deck-module`, in deck/): a trait the code implements – `process(&mut self, block, ctx)` for audio (block-wise, no allocation), `control(&mut self, ctx)` for control rate, optional `video` later as WGSL data (wasm has no GPU, #185). `#[param(range = 0.0..8.0, default = 2.0)]` on fields = the parameters tab; `#[port]` = inputs / outputs with their types (audio / control / video). The SDK generates the descriptor the compiler extracts (the parameters, ports, the ABI version).
- **ctx = the globals, read-only**: the tempo (bpm, beat, phase – the deck clock #181), the character (id, persona, mood, the feelings #188), scene and world variables, the device's controls. Writing back to the world happens through declared outputs (a control output routed to `being:glow`, an event emitted like deck-events' generators) – never by mutating globals, so a module can't break a show.
- **Where it runs (two tiers, Rust first):**
  - **wasm (every draft, every member's module):** compiled to `wasm32-unknown-unknown`, run by wasmtime on a deck (cached compile, instantiate 72 µs, 1.0–2.4× native – the 2026-10-29 measurements, #185) and natively by the browser's engine (live-core in its AudioWorklet). Sandboxed: a module cannot touch files, network or other modules; a trap silences that node, not the show. Hot-reloadable.
  - **native (published factory modules the owner marks):** compiled into the deck image as a cargo feature, the same code (#185's scene-driven builds: a scene names its modules, `deck-scene-features` picks them) – the speed the owner asked for, and no dylibs (no ABI, no sandbox – DECISIONS 2026-10-30). Shipped with `deck-update` bundles (#237). The browser always runs wasm.
- **The compile service**: rustc can't run in a browser or on the FTP hosts. A **build service** – a small Rust HTTP service with a pinned toolchain + the SDK + its dependencies prebuilt into its image (a few seconds per compile) – takes the files, answers the `.wasm` + the descriptor or the compiler's errors as JSON (file, line, column, message).
  - **Where (owner 2026-11-02: "on the same server we run the relay … i will run the entire apps in one magic container on the long run"):** a **second container in the relay's bunny Magic Containers app** (`scutoons-live`), its own image (`scutoons-build`, ghcr.io, its own workflow like `live-image.yml`). bunny runs an app's containers in one pod: they share the network (localhost, one port each), the resources (8 CPU / 32 GiB per pod on a standard account, 10 GB ephemeral disk) and the lifecycle (they start, stop and scale together). That is the first step towards the one-pod platform. If the load ever becomes a problem, **creating (the compiler) and performing (the relay) move to two separate pods** – not now (owner 2026-11-02: "for now it is fine. we wont have that much load"); the service is built so that only its address changes.
  - **What sharing a pod costs, and the rules for it:** (1) **CPU** – there are no per-container limits, so a compile could starve the relay ("performance and stability is everything", #223): one compile at a time, `CARGO_BUILD_JOBS=2` (the relay needs < 1 % of a core), a queue, and **no compiles while the relay reports a live session** (`127.0.0.1:7700/status` → `live > 0`: the request waits or is answered "after the show"). (2) **Lifecycle** – updating either image restarts the pod, the relay too: the deploy freeze of `live-image.yml` (no update while `live > 0`) covers both workflows; and the relay can no longer be stopped between shows while members compile – the pod stays up (cost: one always-on pod instead of a stoppable one). (3) **Start time** – the toolchain image is ~1.5–2 GB against the relay's 3 MB, so a cold pod start takes longer (minutes on a new node, cached after).
  - **Hostile code**: compiling must never run member code on the server. Member crates get no `build.rs`, no proc-macros of their own, no dependencies beyond the SDK's vetted list (the service writes `Cargo.toml` itself, `--offline`); rustc itself gets a time and memory limit (a hostile source can at most waste a compile slot). A module's `#[test]`s run as wasm in wasmtime inside the build container, with fuel and memory limits – never natively. The build container holds no secrets (the relay's `LIVE_TOKEN_SECRET` is the relay container's env only); it is reached through the API, which checks who may compile (§9.3) and stores the result.
  - **The native tier** (published modules the owner marks, in the deck image) is not built here: it is part of the deck image build (deck/os, Docker on the PC / CI), as today.

## 5. Debugging
- **Compile**: rustc's errors at their file and line in the editor (squiggles, a problems list – the same Problems panel the creator has); warnings shown, not blocking.
- **Run**: every port has a scope / meter in the node view (values on the cables); `log!()` in the SDK prints to a console under the editor (rate-limited, per module); a trap (panic, out-of-bounds, a time-budget overrun) silences the node, marks it red and shows the message; a CPU meter per module (µs per block against the budget).
- **Determinism**: a module gets its seed from ctx (like deck-events' generators), so two decks play the same – a test page can render N blocks offline and compare (unit tests for modules: a `#[test]` file in the module runs on the build service).

## 6. Who owns what – drafts, review, publish (owner 2026-11-02: "members who are only readers can not save presets … this entire feature is redundant … we move out of the deck, it is a creator part. more strict is better.")
- **Only creators and admins save anything** – modules, instruments, presets, rigs, assignments – as **drafts of catalog documents** (`module:<id>`, `instrument:<id>`, `preset:<id>`, `rig:<subject>`), within their scope (§8). Review and publish are the creator's normal ones (the review rules; nothing here is physical). History, restore and the lineage come with the documents.
- **Readers (members) save nothing.** No personal presets, no member modules; **there is no submit flow and no promote step at all** (owner 2026-11-02: "remove the submit flow entirely"). A deck plays the published rig of its character (or the standard fallback) – nothing else, and its only own state is the configuration of §8 (performance and hardware settings, per deck instance).
- **Testing a rig assignment** = the creator's Sound page plays the draft in its own engine (the engine host of the creator, #290 / the engine host issue). Hearing it on a real deck means publishing it (the normal review) – no private channel from a draft to a deck.
- **Confirmed = wired to a character:** a published rig assigned to a character plays for everyone. **This mapping is the important part.** The Sound page and the creator's character page show every character **without a default rig**; a deck never fails for lack of one – **the fallback is always a standard rig we provide**, built from one standard instrument per **instrument kind** (drum, bass, lead, pad, voice, sampler, texture, fx – a list we extend in code, `InstrumentKind`), §9.4.
- **The member layer that was built is redundant:** `member_presets` / `member_rigs` (#258 / #270, PR #275: `/api/rigs/*` member routes, the deck token's `rigs` scope, scene-content `&presets=`), `member_modules` (#281), the deck's "Save preset" sheet (`deck-save-sheet.svelte`), F6 on the stage (`deck/stage/src/save.rs`) and `shared/live-deck/src/preset.ts`. Removing it is a cleanup issue (analyse the production rows first, a migration, no silent loss) – until then it stays dormant and unused.
- **Native tier:** a published module may be marked for the native deck build only by the owner, after a manual review (§9.5).

## 7. Where it is stored (the owner's question)
| What | Where | Why |
|---|---|---|
| a module's **source files** (`{ "lib.rs": "…", "osc.rs": "…" }`, + `Cargo.toml` fields the SDK allows) | **in the DB as a versioned document** – factory `module:<id>` in `entity_versions` (drafts, versions, history, restore, review, publish – like items) | everything else is a document already; history and review come free; Shadertoy keeps sources in its DB too. Size: text, small; a limit (e.g. 256 KB per module, 32 files) |
| the **compiled `.wasm`** | **the CDN as an asset**, named by its content hash (`modules/<id>/<hash>.wasm`) – the immutable-paths rule | decks and browsers fetch and cache it like any asset; the same source + toolchain = the same hash |
| the **descriptor** (parameters, ports, ABI version, toolchain, the wasm's hash) | in the module document, written by a successful compile | the parameters tab and the validator read it without running anything |
| **native builds** of marked published modules | the deck image / `deck-update` bundles (deck/os), as today's features | built with the image, signed |
| instruments, presets, rigs, assignments | catalog kinds (#258): drafts and published documents | unchanged; the member rows are redundant (§6) |

Not a git repo per module (heavy, a second history beside the documents), not files on the FTP hosts (not versioned, not reviewable).

## 9a. Two modes: performance and edit (owner 2026-11-02)
Owner: "since we are separating two concepts, performing and editing … we can save resources: we load and lazy-load all the overhead for editing" · "if we split features into those two categories, we can save space and make the UI smarter."
- **Performance = the deck** (the viewer's /live/deck, the native stage): loads and runs only what plays – no designer, no code editor, no validators, no source documents, no dense UI. Its only extra is the configuration of §8.
- **Edit = the creator** (§8). Nothing of editing is on the deck, so the deck needs no switch: the lazy-load rule for the deck is now "nothing of the editor is on this page at all". Inside the creator the Sound page may still lazy-load its heavy parts (CodeMirror, the engine host) when it opens.
- **The rule for every feature:** it is either a *performance* feature (the deck: always on, light, touch-sized, no allocation on the hot path) or an *edit* feature (the creator: heavy, dense where the dense tier allows, creators only). A feature that needs both splits in two.
- Checked by the build: the deck page's chunks must not grow when an edit feature is added (the bundle sizes go into the report of every ticket that touches the deck page).

## 9b. Baked rigs – compile parameters, mappings and moods (owner 2026-11-02: "consider compiling parameters and mappings so we save further resources in runtime")
Today a deck resolves at run time: preset lineages are folded (`PresetBook::resolve`), variants merged (`Rig::play`), parameters found by `node.port` strings, mappings bound from `source` / `target` strings, and the source JSON / TOML is parsed and kept. A **bake** moves all of that to publish time:
- **What is baked** (one binary *rig image* per rig, content-hashed, an immutable path like every asset): per track the folded value table as `(param index, f32)` pairs against the module descriptor's dense parameter ids (no strings); every persona × mood combination precomputed as a small *diff* against the default (switching a mood = applying a short diff, no fold, no allocation); the mappings as one flat table (source id → parameter index, scale, offset – a MIDI CC / face / motion / pad / stick event is one array lookup, no string parsing); the routes as index pairs; the exposed knobs' labels, ranges and curves.
- **Who bakes:** Rust, the same code the engine uses (`deck-space` `rig::bake`), run by the build service in the pod (it already has the toolchain and the SDK) when an instrument, preset, rig or module is **published**; the API stores the image on the CDN and scene-content serves its url + hash next to the source documents (which only the edit mode and the creator read). A change to an instrument re-bakes the rigs that use it (the "uses" relations exist). A member's personal version (F6) stays a short diff applied over the baked parent at load – no re-bake.
- **Performance mode loads only the image** (and the modules' wasm); edit mode loads the sources. The same hash = cached on DECKDATA, offline.
- **Measure first, then build:** the saving is a hypothesis. Step 1 of the issue is a benchmark on the real targets (the X1, the S22 in the browser): load time and memory of source vs image, the cost of a mood switch, the cost per incoming mapped event, allocations in the audio path (`tests/no_alloc.rs`). If the numbers are small, the bake still pays as the *single resolved form* the hot path reads, but it is then done later.
