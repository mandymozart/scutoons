# ENGINE-ALIGNMENT – one engine, one module host, cost you can see

Owner 2026-11-02: "the browser engine is the rust engine. it is just a different compiler target. what is different. we need to keep the deck engine aligned and a single source of truth." · "is there a possibility to monitor how much a module costs during runtime? this would help developing those in the process." · "perhaps in the node view eventually we will have a good place to put these statistics."

## 0. The flaw and what follows (owner 2026-11-02)
**The rule (owner 2026-11-02): "deck-core is everything. with built I mean only lightweight adapters for other browser services and the crate compiler target. really need to stick to one universal core."** All deck logic lives in the universal Rust core (`deck-core` and the crates it is built from – deck-space, deck-events, deck-outputs, the module host, the protocol types), compiled for native and for wasm. A platform contributes only (a) **the compile target** and (b) **thin adapters to the platform's services, with no logic of their own**: native – the audio device callback (cpal / PipeWire / WASAPI), the window and GPU surface, sockets (Link, MIDI, OSC, relay transport), files, thread priority; browser – the worker / ring / worklet, the canvas (WebGPU / WebGL2), Web MIDI, `fetch` / WebSocket, storage. **A test for any file:** if it makes a decision (what plays, when, how loud, how a message is read, which value wins) it belongs in the core; if it only moves bytes or events between the core and a platform service, it is an adapter. TypeScript on the deck side is UI and adapters only.
**What a browser lacks is not worked around:** "browsers that dont support midi are for the moment ignored. if we need a device with midi we can always create native builds on the rust deck-core. that is the intention behind this" – the browser build is the light one (an adapter exists only for a service the browser really has: Web MIDI where it exists, none in Safari); a device that needs MIDI, Link, DMX or any other native service gets a **native build of the same core**, never a TypeScript fallback.
**The browser is UI, no business logic** (owner 2026-11-02: "browser, UI, no business logic."): on the deck side the browser layer shows state and takes input; what to play, how a message is read, which rule applies, what is valid is the core's (or the server's), never a TypeScript copy. **Scope of "browser is UI" (owner 2026-11-02, asked whether it also covers the creator's editor logic):** "editor logic uses the deck-core to render anything sounds, etc. but the ui is built in svelte and holds logic before it is compiled to the core or its modules" – so the line runs between **authoring** and **running**. The editor's Svelte / TypeScript may hold *authoring logic before it is compiled to the core or its modules*: editing state, drafts, selection, layout, jumping to a problem, UX hints (a file-name pattern or a size limit shown before a request). It ends where the core takes over: **rendering, sound, playback and every runtime rule are the core's – the editor uses the core (wasm) for them and never re-implements them**; and what is *valid* is decided by the core or the server – an editor-side check is only a hint, never the authority. (The question was asked after I had read the rule as reaching the whole creator and began to move even the editor's file rules out; the owner's answer narrows it back. The server-side PHP validator of #313 is a different case – a second implementation of core logic on the server, not editor UI.) **Module extensions are Rust and universal** ("module extensions are all in rust and will have to be universal to run with the core in browser and in any other deck."): a module is Rust source compiled to one portable artifact (wasm32) that runs in the core on every deck – native, browser, any other – with the same ABI and no platform imports beyond the core's own (`env.deck_log`); no JavaScript or TypeScript modules; the native tier (a marked module compiled into the deck image) is the same source, and the conformance suite (#305) keeps every build of a module – wasm on each backend and native – equal.
**Other browser devices – camera, position, accelerometer – are reached on a need basis** (owner 2026-11-02: "other browser devices are camera, position, accelerometer. those browser apis, so we can reach them on a need to basis in the deck-core or in any module we write through our creator editor. the sound designer is the proof of concept."): they are platform services like MIDI – a thin adapter feeds them into the core as typed **input channels**, and the core or a module reads them; a module never calls a browser API itself (it stays universal Rust). Proposal (design in #312, extends #212): a module **declares its needs** in its descriptor (e.g. `needs: [motion, position, camera]`; additive to ABI v1); the platform enables an adapter only when a loaded module or scene needs it and the platform has it – the permission prompt comes at a user gesture, only then; a deck without the service (Safari without Web MIDI, a headless deck without a camera) says so and does not run that module; sensor data is processed **on the device** in the core (e.g. face blendshapes computed in wasm, raw frames not handed to modules by default) and nothing leaves the device unless the user starts a stream. **Rigs are Rust running in the core, universal – like modules** (owner 2026-11-02: "the rigs are also fundamentally rust modules running with the core and are universal. i hope you get it."). What is true today: the rig logic – `Rig::play`, `flatten`, the lowering `lower()`, the horizon, `Instrument::check` / `Rig::check` – is Rust in `deck-space` (about 1,400 lines without tests) and the browser already runs it as the core (`rig_play`, `core_rig`, `scene_rig` in space-web). **Consequence:** a rig, an instrument and a preset are *data for that one Rust implementation*, not a format with its own validators per platform; **the server's PHP `RigValidator` (704 lines + the generated `NodeKinds.php`) is a second implementation and must go** – validation comes from the Rust core (via the build service, which already has the toolchain, or a small core-built validator the API calls), the creator only shows its answer (#313). The parked TS validator (`parked/269-rig-editor`) is never revived for the same reason. **Decided (owner 2026-11-02, asked whether a rig can also be authored as Rust code): "of course it is just another layer after the instruments. rigs are module groups."** – the layers of one mechanism: **module** (Rust, wasm, a leaf with ports and parameters) → **instrument** (a graph of modules and built-in nodes, with its exposed knobs) → **rig** (a **module group**: tracks of instruments, routes, persona / mood variants). Every layer runs in the one core with one ABI and one runtime. A layer is written as **data** (the declarative form: the document the core interprets – today's instruments, presets, rigs) or as **Rust code** (a module that has access to the globals – tempo, the character and its parameters, scene / world variables, declared sensors – and drives the layer below through control outputs); the declarative rig is the group that needs no code. #296's bake compiles either form. Design: #314.
**The Sound design workspace is the proof of concept** of the whole architecture – universal core, universal Rust modules written in the creator, compiled by the build service, played by the same engine in the browser and on any deck, thin adapters on a need basis – so each rule above is checked against it first.
Owner, on finding that the native stage runs its own audio engine and does not use the batch graph the browser runs: "this can not be and is a fundamental design flaw". It breaks the rule of #288 – "we dont want to develop stuff double … native vs browser is only a build, not a code base" – on the audio side. Facts: the stage's audio (`deck/native/src/audio`, 4,081 lines: backend / ring / lead / priority for the device, `blocks.rs` fundsp blocks, `voices.rs` osc / fm batches, click, glitch, walk, sequencer, dispatch, module) is built on the same *batch model* (#183) but as a separate implementation of `deck-core`'s `BatchGraph` (561 lines, run by live-core, 575). #288 names the browser-side duplicates (the TS sequencer / LFO / noise) but never plans to move the stage onto the shared engine.
**Direction (to confirm): one engine in `deck-core`.** `BatchGraph` is the engine both targets run; it grows every node kind (noise, seq, click, glitch, mixer, fft, chapter_music, walk, events, `module:*`) with SIMD paths for native AVX2 and wasm simd128; the stage keeps only what is platform: the device callback (cpal / PipeWire / WASAPI), the ring, the lead rule, thread priority, the tempo sources (Link, MIDI clock); the browser shell keeps its worker + ring + worklet. A golden-render conformance suite (#309) is the contract for the migration – kind by kind, the stage switches onto the shared engine only when the render matches.
**The tempo clock is part of the engine too** (owner 2026-11-02, on the browser having no clock: "that is also a problem. the tempo clock should also be part of the deck engine"). Today `deck-core` holds only the pure `TempoMap` (327 lines: beat / frame, position, quantize); the **clock controller** (`deck/native/src/tempo/mod.rs`, 546 lines: sources and their priority, tap, quantized start, the seqlock to the audio thread) and the **sources** (MIDI clock in / out 477, Link 68, OSC 139) live in the stage, and the browser has none – walks use their own bpm, the strobe stays dark, a module's `ctx.tempo` has no source, and the protocol carries **no show clock**, so a phone cannot receive a tempo at all. Direction: the **controller moves into `deck-core`** (the stage's imports are small: a monotonic time source and an event queue become injected; `Graph` / `Kind` is the scene's), so beat, bar and phase for every node – click, seq, walks, modules, the strobe, outputs – come from one clock in both engines; the **sources are platform adapters** feeding it: native Link, MIDI clock, OSC, tap, internal; browser the **relay's show clock** (a new tempo anchor message `{ bpm, per_bar, beat, at }` from the conductor, scheduled with the relay's lead like cues), tap, internal, Web MIDI clock input where the browser has it. The stage's **time base** (`clock.rs`, the DLL that aligns the picture to the audio stamps) stays a platform shim (the browser's equivalent is `AudioContext.getOutputTimestamp()`); only its pure smoothing could be shared.
**Consequence for modules:** a module is a node of **the one engine**, so its hook lives in `deck-core` once – never in the stage's audio and in `BatchGraph` separately. #305 (the host crate, engine-agnostic) can proceed; **#290 and the module-node integration wait for the converged engine.**

## 1. What is different (summary)
- **Picture side: genuinely one code base** – deck-space (3D, rigs, lowering, mappings) and space-web are the same code for wasm; only the GPU backend differs (wgpu native, WebGPU / WebGL2 in the browser).
- **Audio side: not one engine.** The stage runs its own audio runtime (fundsp blocks + `voices.rs` batches) and does **not** use `deck_core::batch::BatchGraph` (grep: only `levels` is imported); the browser runs `BatchGraph` inside live-core. Shared: lanes, math, smooth, limiter, FFT, `TempoMap` (type only). Intended differences: audio I/O (OS callback vs worker → ring → worklet, adaptive lead up to 128 ms), threads (native vs Worker + SharedArrayBuffer), the 3D backend, Web MIDI input only.
- The browser plays only `lfo · smooth · mul · add · osc · fm` (+ walks and events driving a voice's `freq`); everything else is "the page's" (TS / Web Audio) or **not played at all** (`seq`, `click`, `chapter_music`, `glitch`). The browser has **no tempo clock**.

## 2. Behaviour implemented twice today (ranked by risk)
1. **The audio runtime:** stage (fundsp / `voices.rs`) vs `BatchGraph` – the osc / fm voice loop exists twice in Rust; **no test compares the two engines' output** → #309.
2. **Page-side TS DSP and sequencing:** noise (`noise.ts`, `Math.random` – breaks the seed rule), the fixed patch's melody / LFO / mood ladder in `deck.ts` / `scene.ts` → retired by #288 steps 1 and 4.
3. **The module host:** `deck/native/src/module_host.rs` (610 lines, wasmtime) vs `shared/live-core/src/modules.ts` (346 lines, V8 WebAssembly) – only the ABI offsets are generated → #305.
4. **Walk / events host glue:** `live-core/walks.rs` vs `native/src/audio/{walk,sequencer,dispatch}.rs` around the shared `deck-events` crate.
5. **Mood ladder:** TS `Moods` vs `being.rs`. 6. Relay client / sync / lead rule / rings: twins without behaviour tests. 7. Codecs (wire, signals, events, ABI): fixture-tested, fine. 8. **Missing, not doubled:** the browser's tempo clock → #308.
Also: the rig lowering `rig/engine.rs` knows only the six batch kinds, so **`module:*` nodes are silently pushed to the page nodes (unplayed)**; `BatchGraph` needs a module hook.

## 3. One source of truth for running modules
**Recommendation: one Rust host crate `deck-module-host` behind a small `Backend` trait, plus a conformance suite as the contract** (#305). Backends: wasmtime (today's stage), `web` (live-core calls four JS functions into the browser's `WebAssembly`; the JS holds no logic), and **wasmi as a third backend to benchmark**. **No more TS host code**; `modules.ts` is frozen as the fixture reference and deleted when the crate passes the same fixtures.
| Option | Verdict |
|---|---|
| 1 TS host over the browser's WebAssembly (today) | host logic twice; no preemption in the browser |
| **2 Rust host crate, backends behind a trait** | logic once; JIT in both places; browser preemption still needs gas or a watchdog |
| 3 wasmi on both targets | one VM, **fuel and preemption everywhere**, deterministic; interpreter slowdown (anecdotal 5–20× vs a JIT – unmeasured), adds size to live-core; the deck could drop wasmtime |
| 4 native cargo-feature modules for factory tiers | already the decided tier model; native and wasm differ by libm → the suite must keep both honest |
| 5 gas injected at compile time (`wasm-instrument`) | deterministic cost in V8 too; overhead unmeasured; maintenance of the tool unconfirmed |
Why not "wasmi everywhere" yet: readers' phones run published modules in performance mode – an interpreter costs battery and headroom. **Decide after #306.** Wasm float arithmetic is deterministic except NaN payloads and relaxed-SIMD, so two wasm hosts should match bit-for-bit if the SDK forbids relaxed-SIMD – cheap to test.
**Benchmark spec** (#306): `walk`, a 16-voice FM module, a runaway loop, a memory-growth module on wasmtime native, wasmi native, wasmi in the live-core wasm, the browser's WebAssembly, and with gas instrumentation; p50 / p99 / max per 128-frame block, units per block, bit-equality, size gz, over-budget-to-trap latency, peak memory; devices: X1, S22 (Chrome), creator PC (Chrome / Firefox), iOS Safari if available. Suggested gates: FM16 p99 ≤ 25 % of budget on the S22; instrumentation ≤ 1.5×; wasmi bundle ≤ 150 KB gz or creator-only. Existing numbers (deck/lab): wasmtime instantiate 72 µs, cold compile 0.6 s, FM16 128 frames native 34.5 µs / wasmtime 35.8 µs / Chromium worker 49.8 µs; budget 2667 µs per block.

## 4. Can a module's cost be monitored? Yes, partly
- **Measurable everywhere:** wall time per block (p50 / p99 / max, % of the block budget) – native `Instant`; browser `performance.now()` in the **worker** (where the graph runs; not exposed in the AudioWorklet scope), 100 µs resolution (5 µs when cross-origin isolated) so aggregate over many blocks; linear-memory size and growth; events, `log!` rate, traps, overruns, silenced state.
- **A deterministic cost unit** (fuel / gas): the same on the X1, a phone and the creator's browser – answers the **developer's** "is my module too expensive" (a CI assertion) – exists natively (wasmtime / wasmi fuel); in the browser only via a gas-instrumented module or wasmi (#306 decides). **Wall time** answers the show's guard (underruns are caused by time); show a calibration "N units ≈ X µs on this machine". Preemption: native epoch interruption (exists); browser gas trap, or a heartbeat watchdog that terminates the worker (a restart with an audible gap – last resort).
- **Smallest extension** (#307): a fixed-size `ModuleStats` in the host crate updated by the audio thread (two clock reads), `lc_module_stats()` mirroring `lc_signals()` with generated slot offsets, `host.moduleStats` next to `host.peaks`, the native HUD line (the existing `Instance::cpu_us()` has no consumer yet), two optional fields on `DeckQuality` for the conductor (worst module p99 %, silenced count). Allocation-free; module nodes join `tests/no_alloc.rs`.
- **Where it shows (creator only – research/RIG-EDITING.md §9a, nothing on the performance deck page):** the **Nodes tab** of the Sound design workspace – per-module badges (µs / block, % of budget, units, a red state when silenced, the last trap on hover), a heat map by share of the render, a 60-second sparkline kept in the page – cheap for module nodes; built-in nodes are batched per kind, so a per-node cost does not exist (show the batch or a static estimate; design needed); the signal strip's engine-load lamp; the Rust tab's "cost" line after Play; the conductor's per-deck "worst module %".
