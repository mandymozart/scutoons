# EXTERNAL-EDITOR – how good is an existing editor for module code, and what can its autocomplete know

Owner 2026-11-09 (#450): "how good are our options to use an existing editor to write real code … i am mostly concerned about auto complete to know about the world context, so it will make sense to edit in the same software … is there also a split for deck to be build without the editor". Marks: **V** = verified here (command run, dated 2026-11-09), **R** = read in code or docs, **W** = web, 2026-11-09. Sizes as in NATIVE-EDITOR-GUI: S one session, M a few, L a week+.

## 0. The short answer and the recommendation
- **Rust code: external is good, and almost free.** VS Code or Zed with rust-analyzer (§1) know the SDK and our `#[derive(Module)]` once a module folder is a real Cargo project. V: the walk module as a stand-alone project checks in 10.4 s cold, 0.5 s warm, for the host and for `wasm32-unknown-unknown`, and the derive's own errors show by file and line (§4).
- **The world's strings are not free in any editor, and not in ours either.** Ports, parameters, node kinds, addresses, moods, tracks and other modules' descriptors are strings in rig TOML / JSON and in attribute strings; no editor and no schema can complete them without the document's context. They need one thing we build: **`deck-lsp`, a small language server in Rust on the core's own address parser and validate** (§2.3), M.
- **"Same software" does not decide autocomplete.** Completion lives in the server, not the window. The same `deck-lsp` serves VS Code now and a built-in editor later. What the built-in editor would add is live state (running values, the selected node), which is small for completion (§3).
- **Recommended order:** (1) the working folder is a real Cargo project plus editor settings plus one check command (S); (2) `deck-lsp` for rigs and the attribute strings (M); (3) the in-app code editor (L) stays "later", decided after the owner has lived with 1 and 2. The Rust tab stays external as decided 2026-11-09.
- **The deck carries no editor code today, and the plan can keep it so** (§5): V nothing depends on `deck-editor`, and `cargo tree -p deck-native` / `-p deck-update` list none of it.

## 2. What autocomplete can know
### 2.1 The SDK's types: free once the folder is a Cargo project
- NATIVE-EDITOR-GUI §5's "local working copy: one folder per open key holding the sources" is enough if it also holds what `deck/build` writes at compile time: `Cargo.toml` (`compile::manifest`, `deck/build/src/compile.rs:64`: a cdylib, one path dependency on `deck-module`, its own `[workspace]`), `clippy.toml` (`determinism::clippy_toml`) and the SDK sources (`deck/build/sdk/*.Cargo.toml` are the baked manifests of `deck-module`, `-macros`, `-catalog`). R, and V that a path dependency on `deck/module` works from outside the workspace (§4).
- The derive: R `deck/module-macros/src/lib.rs` is an ordinary derive with `#[param]` / `#[port]` helper attributes; it writes `Self::NOTES` style constants per port, the descriptor, and (only `#[cfg(target_arch = "wasm32")]`, line 798) the ABI exports. rust-analyzer expands derives through its proc-macro server (R: a separate process from the toolchain; it needs the toolchain's server to match its own version, a known source of "proc macro not expanded"). **Set `rust-analyzer.cargo.target = "wasm32-unknown-unknown"`** so the exports are analysed too, the same target the service builds. Unverified under rust-analyzer; verified under rustc (§4).
- Offline crates: the service builds `--offline` against a vendored closure. A creator's machine needs the same closure in the folder (`vendor/` plus `.cargo/config.toml`) or network access (S).
- What this does not know: the strings inside attributes (`path = "lead:@preset"`, `reads("story.act")`, `moods = "a|b"`, `names = "music.note"`, `needs = "motion"`): rust-analyzer completes none of them (R, no such feature). The derive checks them at expansion and the editor shows its message.

### 2.2 The service's own rules as diagnostics: yes, one command
- The service's rules are library code: the reject scan (`deck/build/src/scan.rs`, `scan(&Files) -> Vec<Diag>`), the pinned flags and the lint table (`determinism.rs`), rustc's and clippy's messages through `diag.rs` (`Diag { file, line, column, level, message }`). The strict test run (`strict.rs`) is a run of the compiled wasm in wasmtime: seconds, not on every save.
- **`rust-analyzer.check.overrideCommand` takes any command that prints cargo's JSON messages on save** (W: "Override the command rust-analyzer uses instead of `cargo check` for diagnostics on save", default null). Plan: a `deck-build check <folder>` binary mode that runs the scan first (its `Diag`s printed as cargo `compiler-message` lines), then `cargo clippy --target wasm32-unknown-unknown --message-format=json` with `CARGO_ENCODED_RUSTFLAGS` set. Same code as the service, so no second copy (RULES A1, A6). S.
- V without any of that: with the service's `clippy.toml` a stray `f32::sin` already shows as `warning: use of a disallowed method` at its line (1.0 s). So `check.command = "clippy"` plus the folder's `clippy.toml` gives the determinism warnings alone, no new code.
- The same command is what the owner's Claude and CI can run: one check for the editor, the agent and the service.

### 2.3 The strings: three ways, what each costs and completes
| | Cost | Completes / checks | Cannot |
|---|---|---|---|
| **Typed stubs from the catalog** (generated Rust consts) | S–M, regenerated on every catalog change | Rust code that names a port or mood | Nothing in rig TOML / JSON, which is where nearly all the strings are (R: a module's own ports and `reads` already become `Self::` consts via the derive; I found no module code that names *another* module's port). Wrong tool |
| **Schema for the rig document** (taplo, or Tombi, whose language server is replacing taplo in some clients, W) | Free from `deck/catalog/schema.json` (R: generated by `deck-schema`, has `Rig`, `Instrument`, `Preset`, `Bundle`, `Descriptor`, `Track` …): keys, required fields, enums (`PortType`, `Curve`, `Mode` …), hover docs. A per-document schema generated by the core (enum of that document's tracks, nodes and ports) is S–M more | Shape, enums, and with a per-document schema the cable endpoints | Cross-document rules (an instrument id exists, a preset's lineage, a mood in the registry, a far address), the engine's lowering (`Bundle::play`), anything with a computed answer |
| **`deck-lsp`**, a language server in Rust (`lsp-server` + `toml_edit`) on `deck-space` with default features off, as `deck/build` already links it (R: `build/Cargo.toml`, `POST /validate`) | M for rig TOML (completion, hover, diagnostics, go to definition), S–M more for the attribute strings (parse with `syn`, which the macros and the scan already use) | Addresses by grammar (`Address::parse`, `rig/address.rs:109`: after `lead:` the nodes of that track's instrument, after `.` its ports by direction and type); node kinds and parameters with range / unit / doc from the descriptors (`catalog/src/builtin.rs`, a `module:<id>` descriptor); preset, instrument and mood ids; the problems of `rig::validate` (`validate.rs`: `Rig::check`, `Bundle::play` per persona and mood, `Rig::warnings`) as diagnostics | Live values of the running stage (it reads files and a catalog cache, §3) |
- **What the LSP needs from the core:** `Address::parse` and the problem sentences return `Err(String)` / text without a position (R `address.rs`, `problem.rs`): a small change to give them a span or the cable's key, so the LSP can place a squiggle without a second parser. The documents also exist as TOML (`Doc::to_toml` / `from_toml`, `edit.rs:114,124`), so a watched folder holds the same form the core reads.
- **The library it reads** is NATIVE-EDITOR-GUI §5's working copy: instruments, presets, rigs and the descriptors of `module:<id>` from the API, plus the kinds (`server/src/Domain/Rigs/kinds.json` and `GET /api/kinds`). No new source of truth.
- **Rust cannot complete these strings anywhere today**, in the browser Rust tab either (R: `shared/rig-designer/src/editor-cm.ts` has no completion). The external route is therefore not a step back; `deck-lsp` is new value in both worlds.

## 3. Same software or not
**What the owner gains inside our editor:** a click on a node in the stage puts the cursor on its `#[param]`; a cursor in a rig highlights the cable on the stage; the problems list sits beside the 3D; hover on a parameter can show the running value; no second window, no install of an editor.
**What the external route already gives, for S–M:** jump stage → code (`code -g`, `zed path:line`); the watched folder feeds the stage after each save (deck-native's `watch.rs` already polls a scene's TOML and shader files in `--dev`, and the preset file is reloaded when it changes, R); problems from `check.overrideCommand` in the editor and the same list beside the stage; code → stage through an LSP notification, only if wanted.
**What embedding costs (L, a week+, several tickets):** the text widget (rope buffer, selection, undo, scrolling, folding, IME, find) on parley's editing module (R §3 of the GUI note); tree-sitter highlighting; an LSP client with its popups (completion, hover, signature, code actions, rename); **and still rust-analyzer, cargo, the SDK and the wasm target on the creator's machine**, because analysis and local builds need them in both worlds. Embedding replaces the window, not the heavy part. Existing components do not fit: Zed's `editor` crate is GPL-3 (R, GUI §1), GPUI Kit's editor needs GPUI (decided against), browser editors (CodeMirror, Monaco) need a webview (against `[rust-first]`); other Rust editor libraries were not checked.
**Three writers:** an in-app buffer adds a third writer beside the disk and the MCP. An external editor already reloads a changed file; an in-app buffer needs its own merge rule.
**The middle options:** (a) external editor + watched folder + problems beside the stage: S–M, the plan above. (b) `deck-lsp` shared by an external editor and a later built-in one: M, the part that does not get thrown away. (c) embedding an existing component: none found that fits. (d) in-app from day one: L, and every completion still needs (b).
**The owner's Claude:** two routes that both keep working. The folder: Claude edits the files, the watcher feeds the stage, `deck-build check` gives it the same diagnostics as the editor. The MCP: `save_draft` stores the module and links; `compile_module` (#449, `tools/mcp/src/modules.ts`) compiles the newest draft and reports errors by file and line. The working copy syncs with the API by `base` / 409 (GUI §5), so the external editor and Claude editing the same folder is the normal case, and an external editor shows the change at once.

## 5. The performance deck without the editor
- **Direction (V):** `deck-editor` is a bin in the `deck/` workspace; it depends on `deck-native`, `deck-space`, `deck-engine`, `deck-core` (`editor/Cargo.toml`). No other `Cargo.toml` names it; `cargo tree -i deck-editor` lists only itself; `cargo tree -p deck-native -e all --target all` and the same for `deck-update` list no editor crate; `deck-native` has no editor feature. The ISO build names its packages: `-p relay -p bridge -p deck-check -p deck-native -p deck-link -p deck-update` (`deck/os/container/build.sh:26`), and `deck/os/update.sh` builds `deck-update`, so neither builds the editor.
- **One leak, not in the deck:** `.github/workflows/deck.yml:110-111` runs `cargo build --release` and `cargo test` with no `-p`, so CI builds and tests the editor in every matrix cell (cost, not a deck binary). Name the packages, or exclude the editor, when it grows.
- **The other way round:** the editor links `deck-native` with its default features (`sync, chapter, live, midi, osc, outputs …`, `native/Cargo.toml`), so the editor carries the deck's relay, chapter and MIDI code, which it does not need; `default-features = false` when the editor stops being a proof. Not a deck problem.
- **Which planned pieces can end up in a deck**
| Piece | In a deck? | Why |
|---|---|---|
| UI kit (tree, layout, focus, draw list, tokens) | **yes** | [platform] 2026-11-09: #386 uses the same library; no wgpu, wasm-buildable, listed in `scripts/deck-deps.json` as a core crate |
| its wgpu draw adapter, glyph atlas | **yes** | the deck draws with wgpu already (`deck-space` feature `gpu`) |
| text shaping (parley) | **yes, small** | the deck's UI needs text; today `ab_glyph` and a font8x8 HUD raster. Editing (selection, IME, clipboard) behind a kit feature the deck leaves off |
| IME, selection, clipboard (`arboard`) | no, a feature | a touch deck types little (pairing codes) |
| code editor widget, `deck-lsp`, rust-analyzer, local builds (`deck/build` as a library, cargo, wasm target), file watching of a working folder | **no** | editor-only crates; local builds need a toolchain a deck must never hold. Only a module's compiled wasm reaches a deck (decision 2026-11-04, "live/deck runs only final builds") |
- **What keeps them out:** (1) crate boundaries: editor-only crates (`deck-editor`, `deck-lsp`, the code editor, the local-build wrapper) in no dependency list of `deck-native`, `deck-update`, `deck-ui` or a core crate; (2) `check:deck-deps` already fails a core crate that pulls a deny-listed platform library, so the kit and the wire to `deck-ui` stay platform-free; **add one rule: `cargo tree -p deck-native` and `-p deck-update` may list none of an editor deny list** (S, the same `cargo tree` call it makes for the core crates); (3) features for what the deck shares with the editor (text editing). `deck/native/src/main.rs` (1,792 lines, `scripts/native-logic.json`) and `native/src/space/link.rs` may only shrink: nothing above adds to them; the kit and its adapter are new crates that `main.rs` calls.
